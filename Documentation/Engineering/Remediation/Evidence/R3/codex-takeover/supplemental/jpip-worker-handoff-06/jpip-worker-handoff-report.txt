Explicit handoff proof
New JPIPBlockingWorker.run creates JPIPWorkerHandoff on the caller before
starting the dedicated thread. That handoff contains Mutex<Result<Value,Error>?>.
The worker finishes constructing its complete owning success/error result, then
publishes it while holding that mutex. Only after unlocking does it resume a
Void continuation. The caller resumes, acquires the same pre-existing mutex,
takes the result and clears the slot before using any returned owner. Thus every
worker initialization/write precedes the producer unlock, and caller owner use
follows the matching consumer acquire. The continuation carries no connection
reference. This provides an explicit synchronization edge for the unchecked-
Sendable socket's lock objects as well as its response/header owners.

HTTP normal and stale-connection retry outputs use this path. WebSocket
handshake connection/peak outputs use the same path. Existing cancellation-token
binding remains protected by its own lock; failures close their local connection
before publishing an error; callers still await finite worker completion. The
helper deliberately does not abandon work when its caller is cancelled: existing
outer cancellation handlers close the socket and join the worker. Deadline and
generation ownership checks remain in their existing caller paths. No payload
copy or new final image allocation is introduced; the handoff owns a small
constant-sized result wrapper with aliased owning values. Void-only workers do
not export newly constructed socket owners and remain unchanged.
