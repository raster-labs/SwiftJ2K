Separate proposed CI scope
The proposed workflow retains the ordinary complete swift test command. Each sanitizer then builds/lists its own scratch configuration and executes an anchored SwiftJ2KJPIPTests module selection plus the same regex's complement, with the runner's default concurrency inside each partition. The proposed diff changes no assertion, deadline bound, job timeout, serialized trait, worker cap, retry, or sanitizer suppression. set -euo pipefail ensures a failed command cannot yield a passing step. If the first partition fails, the complement remains unexecuted and coverage is incomplete.

The Python helper captures ordinary and sanitizer declaration inventories separately from stderr, preserves raw IDs, rejects empty/malformed/duplicate inventories, and requires exact ordinary/sanitizer identity equality. It derives nonempty disjoint sets P and U-minus-P and records exact command/status/hash evidence. It therefore proves declaration discovery equality and a mathematically complete intended partition. Python syntax parses. I did not execute its subprocess commands.

The helper does not itself reconcile actual started/completed test declarations or generated parameter cases. Its true-valued disjoint/union fields describe derived inventory sets, not execution outcomes. This is an explicit limitation in proposal.txt, not evidence that the regex currently omits tests. Before claiming complete sanitized coverage or adopting the proposed CI gate, preserve and reconcile each actual framework's qualified identities and parameter cases against the ordinary same-source run, require both partitions to finish without real sanitizer diagnostics, and keep skips/oracle non-execution visible. Aggregate totals or successful exit status alone do not replace that reconciliation. The proposed workflow currently emits XML but does not automatically enforce this execution-level proof; the coordinator's evidence review remains required.

Primary SwiftPM 6.3 source confirms that the list subcommand does not accept test filter/skip options, while ordinary execution applies complementary XCTest regex selection and passes arguments through to Swift Testing. Therefore adding `swift test list --filter` is not a valid remedy. The same source sends Swift Testing XML to a *-swift-testing.xml sibling when XCTest is enabled; serial XCTest does not pass through the parallel xUnit generator. Report naming and per-case log/event mapping must be checked on the installed runner rather than assuming one XML contains every test.
