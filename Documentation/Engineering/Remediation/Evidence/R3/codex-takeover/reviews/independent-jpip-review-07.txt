Semantic and complexity proof
JPIPTCPSocket.swift:785–821 initializes a line cursor at readOffset, then advances it once for each examined byte. Bytes before that cursor have been proven not to contain LF. fillOnceLocked only appends, so no previously rejected position can become LF later. The same first LF determines line length, preceding-CR stripping and returned text. Existing search-before-cap checks and unexpected-EOF handling remain in place. Each byte in the scanned line, including LF, contributes exactly one counter increment.

At :825–867 the header loop initially examines all available candidate positions. After a failed scan it remembers max(readOffset, priorCount-3). Any candidate before that point already had all four possible CRLFCRLF bytes available and failed; appending cannot change it. The final three starts are the only positions where a four-byte delimiter may become complete. This overlap also covers LF-LF. Rechecking candidate starts in ascending order and checking CRLFCRLF before LF-LF at each start preserves the old first-match outcome, including overlapping or mixed CR/LF sequences. With one-byte fills, at most four candidate positions are visited per added byte; a prebuffered initial region is scanned once. No delimiter, body, or following-message bytes are consumed differently.

Both helpers run with readLock held. :683–706 appends without compacting; concurrent readers cannot move the buffer. Compaction at :807/:838/:845 occurs only after a complete result has been selected and the helper immediately returns. Local cursor indices therefore never survive a shift or a clearing of the buffer. Returning line slices retain their backing storage through Swift value semantics exactly as before; this lifetime was not changed.

Admission/error/API behavior
The only production changes beyond cursors are two stored Int counters and their package-only readLock-protected accessor (:457–466). Increment is guarded by < Int.max, so long-lived traffic saturates rather than traps or wraps. No public API or Sendable conformance changed. Neither helper changes maxReadBytes:1, any raw header/chunk/body limit, storage admission calculation, timeout, allocation strategy, or error category/message. Header search still precedes its cap test; immediate empty EOF still returns nil only for headers, while partial header/line EOF throws. This review confirms preservation of those existing semantics rather than redefining their limits. Failed scans leave the same buffered data for the caller's existing error/close path.

New test quality
The six socket regressions exercise the actual scanner, not merely a model or elapsed benchmark. They cover both delimiter spellings and every final delimiter split, embedded bare CR, body/sentinel preservation, growing 1/4/16-KiB headers with a 4*n work bound, 128/512/2048-byte chunk extensions/trailers with exact one-visit counts, a 2,000-header101 block, accepted exact-cap versus over-cap chunk lines, unterminated header denial before an absent-body read, and immediate versus partial EOF. Although separate writes can coalesce at the socket, the production helper's one-byte admitted fills still force the relevant fragment boundaries. A stalled negative cap case would produce a timeout/network error and fail the expected CodecError assertion; it cannot silently pass as admission rejection.

Both blocking ends run on dedicated workers. The writer completion is buffered before registration, so there is no lost wakeup; the success path awaits the write result, and the error path closes both ends and drains completion. Fixed finite fixtures and one-second socket inactivity timeouts bound test failures. No existing timeout/assertion was raised or serialization added. These remain socket/parser regressions and do not establish external JPIP or WebSocket-extension interoperability.
