JPIP-B01, P1 — drained WebSocket push payloads escape the cumulative operation compressed-byte budget.

Sources/SwiftJ2KJPIP/JP3DJPIPClient.swift:613–615 obtains a response allowance from transferBudget.cumulativeWireBytes. After the request, 634–636 charges only response.data.count to that shared ledger. The pushed payloads are separately drained and appended at 835–844, with no call that charges their bytes to the operation ledger. JPIPWebSocketReadBudget correctly counts pushes and response body together within one request (JPIPWebSocketTransport.swift:582–599,619–630). However, beginRequest initialises the next request's consumedBody from only the currently queued payload (471), and drainPushes resets that queue to zero (633–637). Consequently the next request reuses bytes already consumed by previous pushed bins.

This is a confirmed accounting-path omission, not a runtime-tested result. It is reachable through the bounded 3D client. Replacing the same complete cached bin on each response keeps the final cache span below maximumCompressedBytes, while accumulatedNew retains each push and the total received compressed payload exceeds that ceiling. Generous workspace/memory ceilings do not prevent it.

Concrete two-round proposed test (not executed here): maximumCompressedBytes=64, ample memory/workspace. Establish cnew using a three-byte EOR response. First region response: send a 50-byte pushed metadata bin, then an eight-byte JPP body containing one zero-length explicit bin and byteLimit EOR. The per-request 61-byte allowance admits 58 bytes. The shared ledger records only 3+8=11. Second response: send a 40-byte full replacement of the same pushed metadata bin, then another eight-byte body ending windowDone. The next request's incorrect 53-byte allowance admits 48 bytes. Total response bodies plus pushed payloads are 109 bytes, but the operation ledger records 19. Current cache span can stay at 40 bytes; accumulated fragments retain the 90 pushed bytes. A subsequent verification failure would not repair the already violated receive bound. Use distinct zero-payload response-bin ID and pushed-bin ID so the response does not replace the pushed payload.

Required repair: expose the exact request-local consumed push/response total, charge each byte exactly once to the transfer ledger before the next request, and apply the same policy to pushes piggybacked during cnew. Preserve pre-body denial, descriptor limits and pause/publication ordering. Test two actual WS request rounds with a pushed replacement and assert the second oversized payload is rejected from its declared prefix before allocation. The current queuedPushesReduceTheNextResponseBodyAllowance test covers only one request and cannot detect this omission.

JPIP-B02, P2 — WebSocket handshake peak is admitted but omitted from operation telemetry.

Sources/SwiftJ2KJPIP/JPIPTCPSocket.swift:1030–1075 computes and carries a conservative HTTP header parsing peak in JPIPHTTPWireResponse. The WebSocket handshake obtains that response at 1164–1165, but returns only the negotiated subprotocol string at 1174; it drops the peak. JPIPWebSocketTransport.swift:979–986 ignores even that selected-string return and provides no handshake peak to the caller. Its independent readBudget starts at zero and beginRequest resets peakBytes at 460–463. JPIPTransport.receiveAdmissionSnapshot at 216–219 reports that readBudget peak, so 2D and 3D operation reports cannot include the handshake phase. The new 3D facade correctly takes max(client, reassembly, verification) at JPIPCodecAPI.swift:617–619, but the client term lacks this earlier phase.

Proposed test: an otherwise valid HTTP 101 handshake with thousands of short legal extra headers, followed by a tiny valid image/volume delivery. Keep the handshake's admitted header bound below the operation limit but above all later phases. Assert the operation reports at least that handshake high-water. The current descriptor-heavy HTTP header test verifies early refusal, not successful handshake reporting.

Required repair: preserve a connection/request handshake high-water through setup and include it in the operation maximum without treating released header storage as still live. This is a narrower A05 reporting defect; the original missing reconstruction phase is repaired.

Source closure observations

A01: JPIP.swift now creates one JPIPTransferBudget per bounded delivery (483), sends it through cnew/cclose (145–183,208–215), admits prior snapshot/candidate overlap before cloning (503–510), consumes response/fragments in a bounded scope, and pre-admits a persistent cache candidate before decode. Reassembly receives limits with outer cache/snapshot owners deducted (636–643), and assembly is cleared before decode (647). The decoder receives surviving cache/queue ownership at 649–654. This closes the original caller-side allowance-loss paths inspected.

A02: JP3DJPIPClient uses remaining cumulative wire and live memory/workspace allowance before HTTP/WS reads, accounts for parsed fragments and returned/spatial/received descriptors before mutation, and validates scalar dimension arithmetic. Snapshot accounting uses current retained storage rather than historical high-water. JPIPWireCodec.decodeStream performs a complete borrowed scan before payload/descriptor materialisation (JPIPResponse.swift:585–766); projection dictionaries are pre-admitted, and addAdmitted validates its full merge before mutating the cache. The remaining cross-request push omission is B01.

A03: raw socket length admission and bounded application-prefix parsing precede payload reads; fragmentation accounts for old/new buffers. The application envelope uses a borrowed Data slice (JPIPWebSocketTransport.swift:132–134), followed by admission before owning response/bin decoding. Queue descriptors are limited. The reader joins its actor handler, ends the source-message scope, and pauses further reads before publishing owning responses (1011–1045,1343–1359). This prevents the previous stale-allowance background-push race in bounded facade calls. Legacy public overloads retain explicitly bounded idle push behaviour. No wall-clock or native result is inferred.

A04: JP3DJPIPIndexer now pre-admits probe/parser metadata before construction (489–521), calculates tile positions without materialising allTiles, budgets geometry/nested slice descriptors, admits split-state plus retained packet slices, counts tile output before reserving it (741–762), and admits complete new output while tile scratch/old output remain live (811–826). Core 2D indexer receives the same callback interface; no additional concrete defect was found in the reviewed delta.

A05: reassembleCodestreamBounded reports its projection/merge plus downstream indexer peak; the facade includes that phase and real verification pixel/copy events. This repairs the original reconstruction omission. B02 concerns a different, earlier handshake phase.

HTTP header follow-up: readHTTPResponse scans raw bytes, header count and longest line before creating text/dictionary structures, then reserves retained headers before body reads.
