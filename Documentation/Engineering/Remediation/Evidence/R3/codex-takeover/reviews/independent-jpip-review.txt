Confirmed findings

JPIP-A01, P1 — 2D delivery does not carry aggregate operation limits across session setup, reassembly and decode.
Sources/SwiftJ2KJPIP/JPIP.swift:144 sends cnew with the transport's default 128 MiB body ceiling, not the caller's ResourceLimits. Its len=3 is an advisory request parameter, not a defensive allocation cap. Lines 158–162 then decode and cache any piggybacked stream without operation admission. requestDeliveredImage reaches this path at 481 before calculating its maxWireBytes at 517.
At 728–731, reassembly receives full limits while the client retains its assembly cache, fragment arrays and wire response. The repaired generator/indexer therefore treat an allowance already occupied by client storage as available. At 761–770, the decoder receives full limits plus only prospective session-cache bytes. pendingSessionBins remains live across that decode (it is read at 778), and its storage is excluded; stateless operation supplies zero retainedExternalBytes despite the reconstructed stream having come from still-retained fragments. Internal reassembler preflight does not fix its caller's missing reservation.
Reproducer proposals: (a) incremental deliverImage with a 4 KiB memory/compressed limit and a peer that returns a 1 MiB cnew response despite len=3; require refusal before buffering. (b) a fragmented JPP delivery with pending fragments and reconstruction/decoding each fitting individually but their sum exceeding the operation cap. Instrument allocation/admission at reassembly and decode entry, not only the eventual thrown error. Pass an operation allowance through cnew/cclose, snapshot/merge and decode, subtract every concurrently retained owner, and include that peak in the report.

JPIP-A02, P1 — 3D transfer/cache growth occurs before the new aggregate snapshot check.
Sources/SwiftJ2KJPIP/JP3DJPIPClient.swift:610–620 caps each HTTP response only by maximumCompressedBytes. It ignores maximumMemoryBytes, already retained storage and the cumulative wire allowance; the cumulative test at 809–818 is after the new response has been buffered. Lines 822–825 decode the entire wire response before admitting the VBAS cache. admitAndStoreWireBins at 639 allocates its projection dictionary before checking limits; 643–658 admits only final VBAS payload/descriptors, not simultaneous response/fragments/caches. Lines 845–872 create returned descriptors, spatial-cache entries and receivedBins without admission. The verification snapshot check at 536–570 comes after all of these allocations. It correctly protects its own snapshot but cannot establish that the earlier public operation stayed within limits.
Reproducer proposals: set maximumCompressedBytes=1 MiB and maximumMemoryBytes=4 KiB, then return a 64 KiB valid Class-6/main-header-plus-bin HTTP response. The transport can buffer it before any memory-limit rejection. Separately return many tiny/zero-payload bins so descriptors dominate; and return multiple byteLimit responses that consume the remaining cumulative allowance. Require rejection before the offending response buffer, projection dictionary, output descriptors or cache entry is created. Deduct live retained storage before reads, parsing and cache updates, and include transient peakPayloadBytes rather than only final projected.totalPayloadBytes.

JPIP-A03, P1 — WebSocket reads and push queues bypass operation body/storage limits.
Sources/SwiftJ2KJPIP/JPIPTransport.swift:182 awaits ws.sendRequest without maxBodyBytes, checking size only at 183. The 3D path likewise calls it without a body limit at JP3DJPIPClient.swift:618 and checks only after return. JPIPWebSocketTransport.swift:710 calls readWebSocketFrame with its default 64 MiB ceiling (JPIPTCPSocket.swift:1123–1125). The payload is allocated before the facade's count check. Unsolicited dataBin/push frames append into receivedDataBins at JPIPWebSocketTransport.swift:983–996 without any cumulative limit; the reader may accumulate arbitrarily many individually legal frames while a request waits. This is independent of the repaired timeout cleanup.
Reproducer proposal: complete a normal WS handshake under a 4 KiB operation limit, then send a valid response frame containing 1 MiB, or repeated dataBin/push frames before a response. Assert refusal from the reader before oversized payload/push retention. Apply a connection/request-owned remaining allowance to frame/message reads and pushed-bin retention; account for simultaneous framing/decoded response copies and fragmentation. An eventual facade error is too late.

JPIP-A04, P1 — 3D JPP reconstruction still admits probes/output separately from live scratch.
Sources/SwiftJ2K3D/JP3DJPIPIndexer.swift:429–472 creates probe, allTiles and potentially fullProbe before local preflight of that storage. The later tileLiveWS counter starts at out.count+tileGeomBytes (542), excluding those retained/parser structures. More decisively, tileBitstream growth is admitted at 667/688, but 709–718 copies that tileBitstream into out while tileBitstream, geometries and per-precinct packet slices remain live. The 705 guard tests final output size, not the new simultaneous copy. The generator's reduced downstream limits cannot repair this internal omission.
Small concrete proposed regression: a valid 1x1x1 Part-10 main header with COD.numLayers=65535, zero decomposition, tileHeaders[0]=empty Data, and no precinct payload. Providing the explicit empty tile header avoids the omitted-tile shortcut at 637. LRCP generates 65,535 one-byte empty packets; an approximately 100 KiB downstream workspace allowance fits the current geometry+tile-buffer counter and final output individually, but both 65 KiB buffers coexist at 718, before counting the other storage. Native validation must derive the exact boundary from actual admitted geometry and confirm rejection before out growth. Also exercise a large header probe under a tight limit. Admit probes, tile grid/parser metadata, split-state plus sliced packets, and the complete output+tile scratch overlap before allocation.

JPIP-A05, P2 — volume operation peak omits the reassembly phase.
Sources/SwiftJ2KJPIP/JPIPCodecAPI.swift:614 reports retainedStreamWorkspace plus verification decoder peak only. reassembleCodestreamThrowing at 561 returns Data without exposing its peak; its projection/merge/snapshot/filter dictionaries and downstream 3D reconstruction scratch disappear from the reported maximum. This is a missing phase even though pixelAllocationCount, peakPixelBytes and copyEvents now correctly forward the real verification decoder report at 629–631. A successful tiny-volume delivery with many metadata/precinct descriptors can make reassembly scratch dominate decode; the report has no mechanism to include it. Carry a conservative measured/admitted reassembly high-water into max(network/cache, reassembly, verification) at the operation boundary. Add a case deliberately dominated by reassembly descriptors, not just an assertion that the report exceeds standalone decode.

Concern requiring targeted qualification, not a wall-clock-confirmed failure

DNS resolution is outside the deadline cancellation mechanism. JPIPTCPSocket.swift:491–495 invokes blocking getaddrinfo before assigning a connecting socket to its cancellation token at 506. Expiry can mark the token but cannot interrupt that resolver call; the off-pool continuation is joined until getaddrinfo returns. HTTP/WS silent established-peer tests do not cover a stalled resolver. Verify a controlled delayed resolver and enforce an end-to-end timeout without abandoning unjoined work. No DNS configuration was changed and no resolver experiment was run by this reviewer.

Repairs supported by this source review, with narrow scope

- Cache grammar: numeric bracket codestream qualifiers, semicolon range lists, sticky scope, bounded range predicates, component c selectors, precinct :L qualifiers, whole-field validation and stateful wildcard/range restrictions are present in JPIPSessionManager.swift:724–994 and JPIPRequest.swift:601–602. Conservative disregard of additive layer/rectangle hints and conservative subtractive removal do not suppress required bytes. The former invented c<codestream> convention and - * flush are removed from the reviewed operation paths. This is not an exhaustive conformance certification.
- Primary authority consulted: ITU-T T.808 V2 (12/2022), C.8.1.1–C.8.1.3. Official ABNF: https://www.itu.int/ITU-T/formal-language/itu-t/t/t808/2022/JPIP%20Request.html . Official normative text: https://www.itu.int/rec/dologin_pub.asp?id=T-REC-T.808-202212-I%21%21PDF-E&lang=e&type=items . It permits conservative incomplete server cache models. Unqualified descriptors default to the first requested codestream or zero absent that request field; this review does not claim broader stream/context support.
- Deadline propagation reaches the initial/probe/follow-up HTTP calls with one absolute deadline. HTTP socket watchdogs, request-owned HTTPS invalidation, and off-actor WebSocket writes with joined cleanup address the earlier blocked-I/O propagation defect in the inspected paths. New elapsed-deadline tests are materially stronger than the former explicit-cancellation test, but their runtime outcome belongs to the root. Trickled HTTPS, blocked WS writes, stale-connection retry and DNS remain separate qualification cases.
- 3D verification really decodes; real decoder pixel/copy telemetry is forwarded; retained caches are now subtracted before reassembly and verification; the snapshot has its own admission. Findings A02/A04/A05 limit closure of RA2-06.
- Generator reassembly reserves merge/snapshot descriptors and payload overlap before passing reduced limits to either indexer. Newly frozen core 2D JPIPCodestreamIndexer.swift:549–687 preflights probe, geometry, layers/packet sequences, retained slices and output scratch. I found no additional concrete defect within that core 2D function in this bounded review; A01 is at its caller. This observation is not a runtime qualification or approval.
- Terminal completion in the reviewed volume facade occurs after the last checkWork (639–642).
